  SECTION 1: SECURITY

[CRITICAL] S1 — debug_headers.php exposes full $_SERVER, all cookies, and all
  request headers to any unauthenticated caller.
  File: php/api/debug_headers.php (line 1-7)
  Impact: Leaks JWT tokens, CSRF tokens, session data, server internals.
  Fix: Delete this file or gate it behind requireAdmin().

[CRITICAL] S2 — auth.php logs FULL cookie values and ALL request headers
  (including Authorization Bearer tokens) to auth_debug.log on every single
  request. The log file is world-readable inside /logs/ and may be accessible
  over HTTP if /logs/ is not blocked.
  File: php/api/auth.php (lines 16-23)
  Impact: JWT tokens, session cookies, CSRF tokens written to disk permanently.
  Fix: Remove the debug file_put_contents block entirely in production.

[CRITICAL] S3 — get_related.php writes a debug log on every single request
  (line 16), continuously growing related_debug.log.
  File: php/api/get_related.php (lines 16, 104)
  Fix: Remove debug logging from production code.

[CRITICAL] S4 — Access-Control-Allow-Origin: * set on ALL API endpoints.
  This allows any website to read authenticated API responses via CORS.
  Files: ALL files in php/api/ (20+ files)
  Impact: Enables CSRF-equivalent cross-origin data access for logged-in users.
  Fix: Replace * with the specific production origin:
       header('Access-Control-Allow-Origin: https://csnexplore.com');

[HIGH] S5 — CSRF validation skipped for GET requests to activity_log.php
  POST endpoint (line 50-51). The POST endpoint accepts unauthenticated
  internal logging without any token check, meaning any external actor can
  inject fake activity log entries by sending a POST request.
  File: php/api/activity_log.php (lines 50-73)
  Fix: Require admin JWT for POST to activity_log or validate a shared secret.

[HIGH] S6 — track_booking.php exposes customer PII (name, email, phone,
  booking notes, status) with NO authentication — just a phone number.
  File: php/api/track_booking.php
  Impact: Anyone who knows a phone number can pull all associated booking data.
  Fix: Add rate limiting (max 5 attempts per IP/hour) and consider email OTP
       verification before revealing booking details.

[HIGH] S7 — Gallery API (gallery.php) allows delete without CSRF validation.
  The requireAdmin() call only checks JWT, not the CSRF token.
  File: php/api/gallery.php (lines 9, 91-114)
  Fix: Add validateCsrf() call at the top of gallery.php.

[HIGH] S8 — config.php production error_reporting(E_ALL) on line 240 means
  ALL errors (including notices, warnings) are reported in production too.
  The block at line 237-241 sets error_reporting(E_ALL) in both local AND
  production branches — the else branch should use E_ALL & ~E_DEPRECATED.
  File: php/config.php (lines 237-241)
  Fix:
    } else {
        error_reporting(E_ALL & ~E_DEPRECATED & ~E_STRICT);
    }

[HIGH] S9 — router.php (used for local dev) has display_errors=1 and
  error_reporting(E_ALL) hardcoded at lines 5-6, which would leak stack traces
  if accidentally deployed to production.
  File: router.php (lines 5-6)
  Fix: Gate these lines behind a dev-only check.

[HIGH] S10 — regenerateBlogHtml() in blogs.php hardcodes a Windows-specific
  absolute path (C:\\xampp\\php\\php.exe) in the exec() fallback on line 182.
  On the production Linux host this silently fails and logs nothing meaningful.
  File: php/api/blogs.php (lines 179-183)
  Fix: Use `php` command (from PATH) rather than the hardcoded XAMPP path:
       exec("php \"$genScript\" blog $blogId > /dev/null 2>&1 &");

[HIGH] S11 — subscribers.php has no CORS headers but other APIs do.
  More importantly it has no Access-Control headers at all, which could cause
  silent fetch failures in browsers that use preflight OPTIONS.
  File: php/api/subscribers.php (lines 1-43)

[HIGH] S12 — gallery.php (admin upload via POST) uses $_FILES['type'] directly
  for MIME validation (line 58) instead of finfo_file(). $_FILES['type'] is
  user-controlled and can be spoofed. A malicious actor could upload a PHP file
  disguised as an image.
  File: php/api/gallery.php (lines 57-60)
  Fix: Use finfo_file() like upload.php does (line 25-27).

[MEDIUM] S13 — CSP in both config.php (line 307) and .htaccess (line 64)
  includes 'unsafe-eval' for script-src. This defeats a major XSS mitigation.
  Fix: Remove 'unsafe-eval' and update any dynamic eval() code to use safer
       alternatives.

[MEDIUM] S14 — CSP allows "https:" as a wildcard for img-src and connect-src,
  meaning any HTTPS URL is permitted. Use specific allowlisted domains instead.

[MEDIUM] S15 — The HSTS header in .htaccess (line 63) uses `env=HTTPS`, which
  only fires on LiteSpeed/Apache when the connection is directly HTTPS. On
  Hostinger with a reverse proxy, $_SERVER['HTTPS'] may not be set even though
  the user is on HTTPS. HSTS may never fire.
  Fix: Send HSTS unconditionally and rely on SITE_URL to determine protocol.

[MEDIUM] S16 — ObjectCache in config.php uses unserialize() (line 77) on
  cached data from disk. If an attacker can write to the cache directory,
  this is a PHP Object Injection vector.
  Fix: Use json_encode/json_decode instead of serialize/unserialize.

[LOW] S17 — The WAF regex in config.php (line 226) reads the raw POST body
  on every single request including large file uploads, which can cause
  memory exhaustion. It also flags legitimate queries containing "SELECT".
  Fix: Apply WAF only if Content-Length is below a threshold, skip for
       multipart/form-data requests.

================================================================================
  SECTION 2: PERFORMANCE
================================================================================

[HIGH] P1 — auth.php writes to disk (auth_debug.log) on EVERY request,
  including every page load that hits the API. File I/O per request is a major
  throughput killer on shared hosting with inode limits.
  File: php/api/auth.php (line 23)
  Fix: Remove this debug block.

[HIGH] P2 — get_related.php fetches ALL active listings from the database
  (line 56: no LIMIT) to do in-PHP sorting/scoring. On a large dataset this
  pulls thousands of rows into memory per request.
  File: php/api/get_related.php (lines 52-56)
  Fix: Move relevance scoring to SQL (ORDER BY FIELD, RAND() with LIMIT) or
       at minimum add `LIMIT 50` to the query.

[HIGH] P3 — sitemap.php has no output caching. On every crawl request it
  runs multiple full-table queries across 6 listing types + blogs. Sitemap
  should be cached as static XML (regenerated hourly via cron).

[HIGH] P4 — database.php runs CREATE TABLE IF NOT EXISTS for rate_limits
  on EVERY connection (lines 81-90), executing a DDL statement on every
  single page load. DDL acquires metadata locks and can cause contention.
  Fix: Check once with a flag file (like the schema init flag).

[HIGH] P5 — admin/admin-header.php loads Tailwind CSS from CDN
  (cdn.tailwindcss.com) on every admin page, which is the full 3MB+ CDN
  script that parses all HTML classes at runtime. This is extremely slow.
  Fix: Use a compiled/purged Tailwind CSS file for the admin panel.

[MEDIUM] P6 — The cron worker.php runs a busy-loop with sleep(2) for up to
  55 seconds, holding a database connection open the entire time.
  On shared hosting with connection limits this wastes a DB connection slot.
  Fix: Use a simple "run once and exit" pattern rather than a 55-second loop.

[MEDIUM] P7 — ObjectCache fallback in config.php creates one file per cached
  key (line 84). With many keys this creates thousands of small files, hitting
  inode limits on Hostinger.
  Fix: Use APCu as the sole in-process cache, or use a single-file cache store.

[MEDIUM] P8 — The service worker precaches hero images and CSS at install time.
  The CACHE_VERSION is 'csn-v7'. After the recent manifest.json and favicon
  updates, this version should be bumped to force clients to refresh caches.
  File: sw.js (line 10)
  Fix: Change CACHE_VERSION to 'csn-v8'.

[MEDIUM] P9 — blogs.php (frontend) runs SELECT * on the blogs table and returns
  the full content column for every blog in the list view.
  File: blogs.php (line 57)
  Fix: Only select id, title, excerpt, image, category, read_time, created_at,
       slug for the listing view. Fetch full content only on detail pages.

[MEDIUM] P10 — Multiple APIs use SELECT * (see full list in Section 5).
  Fetching unused columns wastes bandwidth, parsing time, and memory,
  especially for tables like blogs which have large content TEXT columns.

[MEDIUM] P11 — admin/admin-header.php loads two separate Google Fonts
  stylesheet requests (line 46, 47) which could be merged into one request.

[LOW] P12 — prefetch.js does not check navigator.connection or
  navigator.getBattery() before prefetching on slow/expensive connections,
  which can waste mobile data.

  SECTION 3: RELIABILITY & BUGS
================================================================================

[HIGH] R1 — blogs.php line 182 uses a hardcoded XAMPP path
  (C:\\xampp\\php\\php.exe) in the Linux exec() fallback — this will silently
  fail on the Hostinger production server and static HTML will never regenerate
  after a blog edit.
  Fix: Use `php` binary from PATH on non-Windows systems.

[HIGH] R2 — worker.php has no retry logic. If a job fails (line 83), it's
  marked 'failed' and never retried. Transient email/DB failures cause
  permanent email delivery failure.
  Fix: Add a retry_count column to jobs table; retry up to 3 times with
       exponential backoff before marking as permanently failed.

[HIGH] R3 — verify-email.php (line 20) fetches ALL non-expired verification
  tokens from the database and loops through them doing password_verify().
  This is O(n) where n = number of unverified users. As users grow, this
  becomes slow and exposes a timing side-channel.
  File: verify-email.php (lines 20-22)
  Fix: Store a non-hashed lookup token and query by it, then verify the hash.
       Or use a HMAC-based token that doesn't require database lookup.

[HIGH] R4 — The 404 error document points to /404.php and the 500 error
  document to /500.php, but these files don't exist in the project root
  (not found in the directory listing). ErrorDocument will itself 404.
  File: .htaccess (lines 321-323)
  Fix: Create 404.php and 500.php error pages.

[MEDIUM] R5 — blogs.php API (line 90) sets slug to generateSlug('blogs', 0, ...)
  before the INSERT, then immediately overrides it after INSERT. The initial
  slug written to DB contains ID=0 and gets overwritten in a second UPDATE.
  This is two round-trips to DB and a brief window with an invalid slug.
  Fix: Insert without slug first, then set slug in a single UPDATE with the
       real ID.

[MEDIUM] R6 — comments.php has a local getAuthUser() function (lines 21-30)
  that duplicates the JWT verification logic from jwt.php. If the JWT logic
  changes, this copy may be missed, causing auth divergence.
  Fix: Use getAuthToken() + verifyJWT() from jwt.php directly.

[MEDIUM] R7 — trip_requests.php PUT endpoint does not validate the status
  value before writing it to the database (line 53). Any arbitrary string
  can be stored as the status.
  Fix: Add: if (!in_array($data['status'], ['pending','reviewed','confirmed','cancelled'])) sendError('Invalid status', 400);

[MEDIUM] R8 — subscribers.php creates the newsletter_subscribers table on
  every single request (line 16-21) even when the table exists, incurring
  DDL overhead on every call.
  Fix: Move table creation to the main schema initialization in database.php.

[MEDIUM] R9 — The .htaccess rewrite for blogs (line 270) expects URL pattern
  `/blogs/blogs-1-my-slug` but sitemap.php generates slugs without the
  "blogs-" prefix type (line 27): it generates `id-title.html`.
  There is a mismatch between how the sitemap generates blog URLs and how
  the .htaccess routes them.
  File: sitemap.php (line 27), .htaccess (line 270)

[MEDIUM] R10 — The cron/worker.php lock file (worker.lock) is created but
  never explicitly removed on abnormal exit (process kill, server restart).
  The LOCK_EX lock is released by OS on process end, but the file remains.
  Next run will open and lock the same file, which is fine—but if cron ever
  changes the working directory, the lock path may differ.

[LOW] R11 — settings.php logs a successful action as action_type 'system_init'
  (line 115) even when the action is a caching toggle. The action_type value
  should be 'settings_update' for accuracy.
  File: php/api/settings.php (line 115)

[LOW] R12 — The Object Cache TTL is hardcoded to 3600 seconds (line 77 of
  config.php) regardless of the settings.json ttl configuration. The DB class
  reads settings.json for its TTL but ObjectCache does not.
